What this is

Before B1, nobody could write a real Licensing/Entitlement/Activation endpoint, because four questions hadn't been answered once: how a service talks to Postgres, how it shapes a paginated response, how it shapes an error, and how the three run side by side. B1 answers all four exactly once, in services/shared/, and gives each service a minimal main.py proving the foundation works end to end.

Spin it up locally

Three terminals worth of state, in order. Each block is copy-pasteable from the repo root unless noted.

0 · One-time setup

# venv, if not already created
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# .env — copy from .env.example if you don't have one, confirm this line is set:
#   LICENSING_PG_URL=postgresql://licensing:licensing@localhost:5433/licensing

1 · Bring up Postgres

cd db && docker compose up -d
docker compose ps   # expect: licensing-postgres  Up (healthy)

2 · Load the deep-hierarchy dataset (once per fresh DB volume)

cd ..
LICENSING_PG_URL=postgresql://licensing:licensing@localhost:5433/licensing \
  .venv/bin/python scripts/generate_bulk.py --reset --verify

Finishes in ~20s at default scale. Ends with a verify block totalling ~1.52M rows across 13 tables, 0 FK-integrity failures.

3 · Build and start the service stack

cd services
docker compose up -d --build
docker compose ps

First build takes 1–2 min (shared base image). Expect all three containers at Up (healthy).

4 · Spot-check

curl -f http://localhost:8001/licensing/v1/health/ready
curl -i http://localhost:8001/licensing/v1/_demo   # expect 401, no headers

curl -s \
  -H "mathworks-access-key: dev-key-b1" \
  -H "X-MW-WS-Caller-Id: LICENSING-MCP" \
  -H "mathworks-requestid: smoke-1" \
  http://localhost:8001/licensing/v1/_demo          # expect 200 + a row

Teardown

cd services && docker compose down
cd ../db && docker compose down   # add -v to also drop the data volume

Troubleshooting

ModuleNotFoundError: psycopg

Seen once during this setup — requirements.txt lists psycopg[binary] but the venv hadn't been synced. Fix: .venv/bin/pip install -r requirements.txt before running generate_bulk.py. Containers are unaffected — they install fresh from requirements.txt every build.

Container stuck at starting

docker compose logs <service>. Usual cause: Postgres from step 1 isn't up yet, or the DB volume has stale credentials — cd db && docker compose down -v && docker compose up -d, then redo step 2.

200 but row: null

Bulk data isn't loaded. Re-run step 2 against the same DB volume.

Port already in use

A previous services stack didn't shut down. cd services && docker compose down, then retry.
